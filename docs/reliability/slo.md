## 1. Философия SLO

### 1.1. Зачем нужны SLO

**SLO (Service Level Objective)** — целевой уровень надёжности сервиса,
согласованный между командой и бизнесом.

Без SLO:

```
    ┌──────────────────────────────────────────────────────────────┐
    │  Проблема: нет общего языка между SRE и бизнесом             │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  • SRE: "система работает нормально"                         │
    │  • Бизнес: "клиенты жалуются на медленные ответы"            │
    │  • Продукт: "давайте добавим фичу X"                         │
    │  • Инженер: "у нас p99 latency 2.3 секунды, это ок?"         │
    │                                                              │
    │  → Спор без фактов. Нет объективной оценки.                  │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

С SLO:

```
    ┌──────────────────────────────────────────────────────────────┐
    │  Решение: измеримые цели + error budget                      │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  • SLO: 99.9% availability за 30 дней                        │
    │  • Текущее: 99.94%                                           │
    │  • Error budget: 0.1% = 43.2 минуты                         │
    │  • Использовано: 25 минут (58%)                              │
    │  • Осталось: 18 минут                                        │
    │                                                              │
    │  → Объективная оценка. Понятные решения.                     │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

### 1.2. Принципы

```
    ┌──────────────────────────────────────────────────────────────┐
    │                                                              │
    │  1. SLO — это договор, не приказ.                            │
    │     SRE и Product Owner согласуют вместе.                    │
    │                                                              │
    │  2. SLO должен быть достижим, но не тривиален.                │
    │     100% reliability — неправильная цель.                    │
    │     (слишком дорого, тормозит innovation)                    │
    │                                                              │
    │  3. Измеряем с точки зрения клиента.                         │
    │     Не "сервер отвечает 200 OK", а "клиент получает          │
    │     корректный ответ за разумное время".                     │
    │                                                              │
    │  4. Error budget — это инструмент, не наказание.             │
    │     Исчерпание budget = сигнал остановить риск,              │
    │     не "вина команды".                                       │
    │                                                              │
    │  5. SLI измеряются на границе системы.                       │
    │     Не на внутренних компонентах, а на client-facing API.    │
    │                                                              │
    │  6. SLO обновляются по мере роста зрелости.                  │
    │     Начать с мягких целей, ужесточать постепенно.            │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

### 1.3. Терминология

```
    ┌──────────────────┬──────────────────────────────────────────┐
    │ Термин           │ Определение                              │
    ├──────────────────┼──────────────────────────────────────────┤
    │ SLI              │ Service Level Indicator — измеряемый     │
    │                  │ показатель (например, latency p99)       │
    │                  │                                          │
    │ SLO              │ Service Level Objective — целевое        │
    │                  │ значение SLI (например, p99 < 2s)        │
    │                  │                                          │
    │ SLA              │ Service Level Agreement — контракт с     │
    │                  │ клиентом (включает штрафы)               │
    │                  │                                          │
    │ Error Budget     │ 1 - SLO. Сколько "плохого" допустимо     │
    │                  │ (например, 0.1% = 43.2 мин/месяц)        │
    │                  │                                          │
    │ Burn Rate        │ Скорость исчерпания error budget.        │
    │                  │ 1x = норма, 14.4x = критично             │
    │                  │                                          │
    │ Toil             │ Ручная операционная работа,              │
    │                  │ которую можно автоматизировать           │
    │                  │                                          │
    └──────────────────┴──────────────────────────────────────────┘
```

## 2. SLI: Service Level Indicators

### 2.1. Формат SLI

Каждый SLI определяется как **соотношение**:

```
    SLI = (количество "хороших" событий) / (количество всех событий)
```

Это даёт **процент** (0-100%), который легко сравнивать с SLO.

### 2.2. Каталог SLI

```
    ┌──────────────────────────────────────────────────────────────┐
    │  SLI-1: Availability                                         │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Определение:                                                │
    │  Доля успешных запросов / все запросы                        │
    │                                                              │
    │  "Хорошее" событие:                                          │
    │  • HTTP status 2xx или 3xx                                   │
    │  • ИЛИ: корректный MCP-response (не error)                   │
    │                                                              │
    │  "Плохое" событие:                                           │
    │  • HTTP 5xx                                                  │
    │  • Timeout (клиент не получил ответ)                         │
    │  • Connection reset                                          │
    │                                                              │
    │  Что НЕ считается плохим:                                    │
    │  • HTTP 4xx (кроме 429) — ошибка клиента                     │
    │  • HTTP 429 (rate limit) — осознанное поведение              │
    │  • Отмена клиентом (client_disconnect)                       │
    │  • Отказ upstream (учтён в Dependencies SLO)                 │
    │                                                              │
    │  Формула (PromQL):                                           │
    │  sum(rate(mcp_requests_total{status!~"5.."}[5m]))            │
    │  /                                                           │
    │  sum(rate(mcp_requests_total[5m]))                           │
    │                                                              │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  SLI-2: Latency (без upstream LLM)                           │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Определение:                                                │
    │  p99 latency для "быстрых" методов (tools/list, resources)   │
    │                                                              │
    │  Измеряется:                                                 │
    │  • от получения запроса gateway'ем                           │
    │  • до отправки первого байта ответа клиенту                  │
    │  • ИСКЛЮЧАЯ время upstream (для методов без upstream)        │
    │                                                              │
    │  Формула (PromQL):                                           │
    │  histogram_quantile(0.99,                                    │
    │    sum(rate(mcp_request_duration_seconds_bucket{             │
    │      method=~"tools/list|resources/.*"}[5m]))                │
    │    by (le)                                                   │
    │  )                                                           │
    │                                                              │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  SLI-3: Latency (с upstream LLM)                             │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Определение:                                                │
    │  p99 latency для tools/call (с upstream LLM)                 │
    │                                                              │
    │  Измеряется:                                                 │
    │  • от получения запроса gateway'ем                           │
    │  • до полного ответа клиенту (или первого чанка для SSE)     │
    │  • ВКЛЮЧАЯ время upstream                                    │
    │                                                              │
    │  Формула (PromQL):                                           │
    │  histogram_quantile(0.99,                                    │
    │    sum(rate(mcp_request_duration_seconds_bucket{             │
    │      method="tools/call"}[5m]))                              │
    │    by (le)                                                   │
    │  )                                                           │
    │                                                              │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  SLI-4: Correctness                                          │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Определение:                                                │
    │  Доля запросов, где audit log записан успешно                │
    │                                                              │
    │  Обоснование:                                                │
    │  Audit log — критичен для compliance. Запрос без audit-      │
    │  записи не должен считаться "успешным", даже если            │
    │  клиент получил 200 OK.                                      │
    │                                                              │
    │  Формула (PromQL):                                           │
    │  sum(rate(mcp_requests_total{audit_logged="true"}[5m]))      │
    │  /                                                           │
    │  sum(rate(mcp_requests_total[5m]))                           │
    │                                                              │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    │  Целевой SLO: 99.99% (см. ниже)                              │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  SLI-5: Rate Limit Accuracy                                  │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Определение:                                                │
    │  Доля запросов, где rate limit применён корректно            │
    │                                                              │
    │  "Корректно" =                                               │
    │  • allowed когда count < limit                               │
    │  • denied когда count >= limit                               │
    │                                                              │
    │  Формула (PromQL):                                           │
    │  sum(rate(mcp_rate_limit_decisions_total{                    │
    │    correct="true"}[5m]))                                     │
    │  /                                                           │
    │  sum(rate(mcp_rate_limit_decisions_total[5m]))               │
    │                                                              │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  SLI-6: Audit Integrity                                       │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Определение:                                                │
    │  Доля успешных проверок hash-chain audit log                 │
    │                                                              │
    │  Формула (PromQL):                                           │
    │  sum(rate(mcp_audit_verify_runs_total{result="success"}[1h]))│
    │  /                                                           │
    │  sum(rate(mcp_audit_verify_runs_total[1h]))                  │
    │                                                              │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    │  Целевой SLO: 100% (никаких компромиссов)                    │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

### 2.3. Сводная таблица SLI

```
    ┌──────┬──────────────────────┬──────────────┬─────────────────┐
    │ ID   │ SLI                  │ Тип          │ Метрика         │
```

## 3. SLO: Service Level Objectives

### 3.1. Основные SLO

```
    ┌──────────────────────────────────────────────────────────────┐
    │  SLO-1: Availability                                         │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Цель: 99.9% за 30 дней                                      │
    │                                                              │
    │  Error budget: 0.1% = 43.2 минуты за 30 дней                 │
    │                                                              │
    │  Обоснование:                                                │
    │  • 99.9% — стандарт для enterprise SaaS                     │
    │  • 99.95% — для critical tier (см. per-tenant)               │
    │  • 99.99% — слишком дорого, тормозит innovation              │
    │                                                              │
    │  Как измеряем: SLI-1 (availability)                          │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  SLO-2: Latency (без upstream LLM)                           │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Цель: p99 < 2 секунды за 30 дней                            │
    │                                                              │
    │  Error budget: 1% запросов могут превысить 2s                │
    │                                                              │
    │  Обоснование:                                                │
    │  • tools/list, resources/read — не должны тормозить          │
    │  • 2s — комфортно для пользователя                           │
    │  • Redis round-trip ~1ms, audit write ~5ms, overhead низкий  │
    │                                                              │
    │  Как измеряем: SLI-2 (latency no LLM)                        │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  SLO-3: Latency (с upstream LLM)                             │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Цель: p99 < 30 секунд за 30 дней                            │
    │                                                              │
    │  Error budget: 5% запросов могут превысить 30s               │
    │                                                              │
    │  Обоснование:                                                │
    │  • LLM может генерировать длинные ответы                     │
    │  • 30s — типичный timeout для upstream                       │
    │  • Включает: rate limit + PII redaction + LLM + PII unmask   │
    │                                                              │
    │  Как измеряем: SLI-3 (latency with LLM)                      │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  SLO-4: Correctness (audit completeness)                     │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Цель: 99.99% за 30 дней                                     │
    │                                                              │
    │  Error budget: 0.01% = 4.32 минуты за 30 дней                │
    │                                                              │
    │  Обоснование:                                                │
    │  • Audit log критичен для compliance                         │
    │  • Запрос без audit-записи — compliance violation            │
    │  • 99.99% — практически не допускает пропусков               │
    │                                                              │
    │  Как измеряем: SLI-4 (correctness)                           │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    │  Alert threshold: >0 failures за 5 минут → critical          │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  SLO-5: Audit Integrity                                      │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Цель: 100% (никаких компромиссов)                           │
    │                                                              │
    │  Error budget: 0 (любое нарушение — critical incident)       │
    │                                                              │
    │  Обоснование:                                                │
    │  • Если hash-chain нарушен — audit log скомпрометирован      │
    │  • Не может быть "допустимого" уровня нарушения integrity    │
    │  • Любое нарушение — critical alert + freeze gateway         │
    │                                                              │
    │  Как измеряем: SLI-6 (audit integrity)                       │
    │  Окно: каждые 5 минут continuous verification                │
    │                                                              │
    │  Alert threshold: 1 failure → critical (page on-call +       │
    │  security team + auto-freeze)                                │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  SLO-6: Rate Limit Accuracy                                  │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  Цель: 99.95% за 30 дней                                     │
    │                                                              │
    │  Error budget: 0.05%                                         │
    │                                                              │
    │  Обоснование:                                                │
    │  • Rate limit должен быть точным (compliance + FinOps)       │
    │  • False negative (allowed когда должен denied) → abuse     │
    │  • False positive (denied когда должен allowed) → плохой UX  │
    │  • 99.95% — компромисс с distributed state (Redis)           │
    │                                                              │
    │  Как измеряем: SLI-5 (rate limit accuracy)                   │
    │  Окно: 30 дней rolling                                       │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

## 4. Per-tenant SLO

### 4.1. Tier-based SLO

Разные tier'ы тенантов получают разные SLO. Это отражает **разную
ценность** клиентов и **разные компенсации** при нарушении.

```
    ┌──────────────────────────────────────────────────────────────┐
    │                                                              │
    │  Tier         Availability   p99 (no LLM)  p99 (with LLM)   │
    │  ─────────    ────────────   ───────────   ──────────────   │
    │                                                              │
    │  Enterprise   99.95%         < 1s          < 20s            │
    │  Standard     99.9%          < 2s          < 30s            │
    │  Free         best-effort    < 5s          < 60s            │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

### 4.2. Обоснование tier'ов

```
    ┌──────────────────────────────────────────────────────────────┐
    │  Enterprise tier:                                            │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  • Платит за SLA с финансовыми гарантиями                    │
    │  • Критичные бизнес-процессы                                 │
    │  • Fail-closed при отказе Redis (лучше 503, чем abuse)       │
    │  • Dedicated resources (изоляция от noisy neighbor)          │
    │  • 24/7 поддержка                                            │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  Standard tier:                                              │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  • Платит за использование                                   │
    │  • Business hours поддержка                                  │
    │  • Fail-open при отказе Redis (доступность важнее)           │
    │  • Shared resources                                          │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐
    │  Free tier:                                                  │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  • Бесплатно (демо, trial, dev)                              │
    │  • Best-effort, без гарантий                                 │
    │  • Community support                                         │
```

## 5. Error Budget Policy

### 5.1. Что такое error budget

```
    Error Budget = 1 - SLO

    Пример:
    • SLO: 99.9% availability
    • Error Budget: 0.1% = 43.2 минуты за 30 дней
    • Это значит: до 43.2 минут "плохого" поведения допустимо
```

### 5.2. Burn rate

**Burn rate** — скорость исчерпания error budget.

```
    ┌──────────────────────────────────────────────────────────────┐
    │                                                              │
    │  Burn rate = (текущий error rate) / (допустимый error rate)  │
    │                                                              │
    │  1x = норма (error budget исчерпается ровно за 30 дней)      │
    │  2x = в 2 раза быстрее → исчерпается за 15 дней              │
    │  14.4x = критично → исчерпается за ~2 дня                    │
    │                                                              │
    │  Формула (PromQL) для 1h окна:                               │
    │  (                                                           │
    │    sum(rate(mcp_requests_total{status=~"5.."}[1h]))          │
    │    /                                                         │
    │    sum(rate(mcp_requests_total[1h]))                         │
    │  ) / (1 - 0.999)                                             │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

### 5.3. Политика

```
    ┌──────────────────────────────────────────────────────────────┐
    │  Error Budget Policy:                                        │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  ✅ Budget > 50%                                             │
    │     • Normal operation                                       │
    │     • Feature releases разрешены                             │
    │     • Рискованные изменения разрешены                        │
    │                                                              │
    │  ⚠️  Budget 20-50%                                           │
    │     • Feature releases разрешены с caution                    │
    │     • Требуется review для risky changes                     │
    │     • Начать планирование reliability work                   │
    │                                                              │
    │  🟡 Budget 10-20%                                            │
    │     • Feature releases только small/critical                  │
    │     • Reliability work приоритет                              │
    │     • Weekly reliability review                              │
    │                                                              │
    │  🟠 Budget 1-10%                                             │
    │     • Freeze feature releases                                │
    │     • Только bug fixes и reliability work                    │
    │     • Daily reliability review                               │
    │                                                              │
    │  🔴 Budget < 1% (или 0)                                      │
    │     • Full freeze всех non-critical changes                  │
    │     • Incident review обязателен                             │
    │     • Escalation к Engineering Leadership                    │
    │     • Root cause analysis                                    │
    │     • Action plan для восстановления budget                  │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

### 5.4. Кто принимает решения

```
    ┌──────────────────────────────────────────────────────────────┐
    │                                                              │
    │  Budget > 50%      → Tech Lead (без согласования)            │
    │  Budget 20-50%     → Tech Lead + Product Owner               │
    │  Budget 10-20%     → Tech Lead + Product Owner + SRE         │
    │  Budget 1-10%      → + Engineering Manager                   │
    │  Budget < 1%       → + VP Engineering                        │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

### 5.5. Исключения

```
    ┌──────────────────────────────────────────────────────────────┐
    │  Что НЕ тратит error budget:                                 │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  • Плановое обслуживание (maintenance window)                │
    │    — анонсировано минимум за 7 дней                          │
    │  • Отказ upstream LLM provider (см. Dependencies SLO)        │
    │  • Клиентские ошибки (4xx)                                   │
    │  • Rate limit denials (429) — осознанное поведение           │
    │  • Клиентские отмены (client_disconnect)                     │
    │  • Force majeure (датацентр,自然灾害)                        │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

## 6. Alerting

### 6.1. Multi-window multi-burn-rate alerting

Классический подход Google SRE: **несколько окон** с разными порогами.

```
    ┌──────────────────────────────────────────────────────────────┐
    │  Burn rate alerts:                                           │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  • Long window (1h) + short window (5m)                      │
    │  • Long — сглаживает шум                                     │
    │  • Short — быстрая реакция                                   │
    │  • Оба должны быть выше порога                               │
    │                                                              │
    │  Пороги:                                                     │
    │  • 14.4x за 1h + 14.4x за 5m → critical (page)               │
    │  • 6x за 6h + 6x за 30m → warning                            │
    │  • 3x за 24h + 3x за 2h → warning (тикет)                    │
    │                                                              │
    │  Обоснование:                                                │
    │  • 14.4x за 1h → исчерпает месяц budget за 2 дня             │
    │  • 6x за 6h → исчерпает за 5 дней                            │
    │  • 3x за 24h → исчерпает за 10 дней                          │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘
```

### 6.2. Каталог алертов

```
    ┌──────────────────────────────────────────────────────────────┐
    │  🔴 CRITICAL (page on-call):                                 │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  • Availability burn rate >14.4x за 1h (и >14.4x за 5m)      │
    │  • SLO-5: Audit integrity failure (1 любой)                  │
    │  • SLO-4: Correctness failure rate >0 за 5m                  │

    │  • SPIRE agent недоступен >2m                                │
    │  • Redis недоступен >1m (для enterprise tier)                │
    │  • HMAC key rotation failed                                  │
    │  • Audit verify failed (целостность нарушена)                │
    │                                                              │
    └──────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────┐

    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  • Availability burn rate >6x за 6h                          │
    │  • Availability burn rate >3x за 24h                         │

    ┌──────────────────────────────────────────────────────────────┐
    │  🟢 INFO (ticket, no page):                                  │
    ├──────────────────────────────────────────────────────────────┤
    │                                                              │
    │  • Новый тенант активирован                                   │
    │  • Config change                                             │
```

### 6.3. Пример alert rule (Prometheus)

```yaml
groups:
  - name: mcp-gateway-slo
    interval: 30s
    rules:
      # CRITICAL: availability burn rate 14.4x
      - alert: MCPGatewayAvailabilityBurnRateCritical
        expr: |
          (
            sum(rate(mcp_requests_total{status=~"5.."}[1h]))
            / sum(rate(mcp_requests_total[1h]))
          ) / (1 - 0.999) > 14.4
          and
          (
            sum(rate(mcp_requests_total{status=~"5.."}[5m]))
            / sum(rate(mcp_requests_total[5m]))
          ) / (1 - 0.999) > 14.4
        for: 2m
        labels:
          severity: critical
          slo: availability
        annotations:
          summary: "MCP Gateway availability burning budget too fast"
          runbook: "https://github.com/realrvs/mcp-gateway/blob/main/docs/reliability/runbook.md#availability-burn-rate"

      # WARNING: availability burn rate 6x
      - alert: MCPGatewayAvailabilityBurnRateWarning
        expr: |
          (
            sum(rate(mcp_requests_total{status=~"5.."}[6h]))
            / sum(rate(mcp_requests_total[6h]))
          ) / (1 - 0.999) > 6
          and
          (
            sum(rate(mcp_requests_total{status=~"5.."}[30m]))
            / sum(rate(mcp_requests_total[30m]))
          ) / (1 - 0.999) > 6
        for: 15m
        labels:
          severity: warning
          slo: availability

      # CRITICAL: audit integrity failure
      - alert: MCPGatewayAuditIntegrityFailure
        expr: increase(mcp_audit_verify_runs_total{result="failure"}[5m]) > 0
        for: 0m
        labels:
          severity: critical
          slo: audit_integrity
        annotations:
          summary: "Audit log integrity check failed - possible tampering"
          runbook: "https://github.com/realrvs/mcp-gateway/blob/main/docs/security/incident-response.md#audit-tampering"
```

## Приложение A: Формулы

### A.1. Error budget

```
    Error Budget (в минутах за 30 дней) = (1 - SLO) × 30 × 24 × 60

    Пример:
    SLO = 99.9%
    Error Budget = 0.001 × 30 × 24 × 60 = 43.2 минуты
```

### A.2. Burn rate

```
    Burn Rate = (error_rate) / (1 - SLO)

    Пример:
    error_rate = 0.5% (0.005)
    SLO = 99.9%
    Burn Rate = 0.005 / 0.001 = 5x

    Это значит: budget исчерпается за 30/5 = 6 дней
```

### A.3. Time to exhaustion

```
    Time to Exhaustion = (Error Budget remaining) / (current error rate)

    Пример:
    Budget remaining = 0.05%
    current error rate = 0.5%
    Time = 0.05% / 0.5% × 30 days = 3 days
```
